# 工具授權

## 範圍

- 涵蓋：run 中後端要求使用者允許或拒絕工具呼叫時，SDK 的授權佇列、內建授權卡片、host 自己做卡片的接法，以及回覆後的通知。
- PM 規格：PM 沒有對應規格。來源是 [freyr-pm#331](https://github.com/asgard-ai-platform/asgard-freyr-pm/issues/331)、[freyr-pm#885](https://github.com/asgard-ai-platform/asgard-freyr-pm/issues/885)、[freyr-pm#901](https://github.com/asgard-ai-platform/asgard-freyr-pm/issues/901)。
- 優先順序：產品規則以 PM 規格為準，實際行為以程式為準；本章只記兩者都讀不出來的決定、差異與限制。

## 設計決定

| 編號       | 決定                                                                                                                            | 類型                  | 為什麼                                                                                                                                                                                                            | 出處                    |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| CONSENT-3  | 一批都是自動代答時也由佇列送出，所以 run 可能觸發授權的期間，佇列必須一直掛著。不要只在有 `pendingCall` 時才掛                  | 刻意的行為            | 自動代答的那一批不會出現任何卡片；佇列沒掛著就沒有人送出回覆，run 會一直停著                                                                                                                                      | 原 BUILD-086            |
| CONSENT-4  | 回覆被拒時把 `pendingConsent` 還原、從這一批第一個呼叫重新回答；但整批都是自動代答的被拒批次不自動重送                          | 刻意的行為            | 自動重送會無限重試同一個被拒的回覆                                                                                                                                                                                | 原 BUILD-073、BUILD-086 |
| CONSENT-6  | 同一個 channel 上 `pendingConsent` 變成 `null`，就丟掉這一批、不送出                                                            | 理由                  | core 裡 `pendingConsent` 唯一被清成 `null` 的地方是 `replyToolCallConsents`，其他轉換與 channel 重建都原樣帶過，所以同 channel 的 null 只可能是「有人回覆了」。原本 #455 R5 的反向規則因此改寫（2026-10-01 確認） | 原 BUILD-086            |
| CONSENT-8  | 開放「`toolCallConsent="off"` ＋ 公開佇列 hook」讓 host 就地畫卡片，不做 render prop，也不只給停用開關；命名比照 `fileExplorer` | PM 未定義、前端先決定 | render prop 只能畫在授權元件那一格（footer 之後），就地卡片會落在 composer 下方；只給停用開關，host 得自己重寫自動代答、同批「這個對話都允許」、被拒還原與重設作廢                                                | 原 BUILD-086            |
| CONSENT-9  | `onToolCallConsentReply` 在續跑的第一個 frame 到達時觸發，不在送出請求時觸發                                                    | 理由                  | 送出不代表被接受；以後端開始回應為準，被拒的回覆不會誤報                                                                                                                                                          | 原 BUILD-085            |
| CONSENT-15 | 佇列不保留「自己送出中」的例外狀態。不要加回去                                                                                  | 刻意的行為            | 佇列只在答完時送出，那時丟掉不會失去任何東西；被拒時 core 先還原 `pendingConsent`，佇列會重新 seed。兩種寫法在所有測試下行為相同                                                                                  | 原 BUILD-086            |

## 已知限制

| 編號       | 限制                                              | 原因                                                                                                                                                                  | 待誰處理            |
| ---------- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| CONSENT-17 | 同一個 `toolCallId` 可能回報兩次                  | 回覆被接受、續跑送出第一個 frame 之後才斷線（且沒有續傳游標）時，callback 已觸發，但 core 仍會把 `pendingConsent` 放回，使用者可能再答一次。host 以 `toolCallId` 去重 | #410 既有取捨       |
| CONSENT-18 | `'builtin'` 時再呼叫佇列 hook，同一批會被回覆兩次 | 兩份佇列各自送出，SDK 不偵測；自己做卡片只能搭配 `'off'`                                                                                                              | —                   |
| CONSENT-19 | 被拒過的舊呼叫在之後每個新訊息被重新詢問          | 後端行為（dev 實測）：以原 id 再發一次 consent，沒有新的 `tool_call.start`                                                                                            | 後端（asgard-core） |
| CONSENT-20 | 答覆以工具為單位套用到整個續跑                    | 後端行為：「僅此次允許」後同一支工具的新呼叫不再詢問；「拒絕」也會套到使用者剛要求的新呼叫                                                                            | 後端（asgard-core） |
| CONSENT-21 | 多筆一批時，被允許的呼叫以新 id 重跑              | 後端行為：原 id 之後沒有 `tool_call.complete`，改以新 id 各送 `start`／`complete`；單筆時以原 id 只回 `complete`                                                      | 後端（asgard-core） |
