# 現況規格（current-state spec）

這個目錄是寫給之後接手的 agent 讀的：只記 PM 規格和程式都讀不出來的東西。章節清單在 [`_index.md`](_index.md)，已收斂的任務在 [`converged-tasks.md`](converged-tasks.md)。

## 這裡寫什麼、不寫什麼

- **寫**：會影響之後修改判斷、而且沒有其他可靠來源的事：
  - 為什麼這樣做，包括捨棄了哪個方案
  - 哪些行為是刻意的：看起來像 bug 或不自然，其實不要改
  - 刻意不照 PM 規格或設計原型的地方，以及是誰、在哪裡核准的
  - 做不到或還沒處理的事：REVIEW 留下的缺陷、延後的工作、還沒驗證的部分
- **不寫**：
  - 路由、文案、數值、檔案位置：讀程式就有，寫進來只會過期。
  - 產品規則本身：在 PM repo（`references/asgard-sdk-pm/`），各章只連過去。
  - 程式註解已經完整講清楚的理由：不要再抄一份。但跨檔案的約束、刻意偏離原型或 PM 的地方，即使註解有寫，也要在這裡留一條短的入口。
  - 還在進行中的需求：留在 `requirements/tasks/` 的 BUILD／REVIEW。
  - 開發過程（誰在哪天改了什麼）：在 git 歷史與封存索引。

PM 規格的連結指向 `references/` 底下的 submodule，要先 `git submodule update --init --recursive` 才打得開。

## 優先順序

產品規則看 PM 規格，實際行為看程式，本目錄只記兩者之間的差異與理由。三者講法不同時：要知道「該怎樣」看 PM，要知道「現在怎樣」看程式，要知道「為什麼不一樣、能不能改」看這裡。

## 每章的格式

每章固定四段，標題逐字照用；某段沒有內容時，標題下只寫一行「無」。

1. **範圍**：涵蓋哪些畫面、PM 規格的相對路徑連結、優先順序。
2. **設計決定**：欄位是編號、決定、類型、為什麼、出處。類型三選一，逐字寫：
   - `理由`：做法本身看得到，但為什麼這樣做讀不出來。
   - `刻意的行為`：看起來像 bug 或不自然，其實是刻意的，不要改回去。偏離 PM 或原型的，要寫出核准的來源（決議、PM 回覆、裁示日期）。
   - `PM 未定義、前端先決定`：PM 規格沒寫，前端暫定了一種。PM 驗收整張票，不代表逐項核准了這些決定；PM 之後另有規定時以 PM 為準。
   - 出處寫 `原 BUILD-NNN`。實作、核准、缺陷來自不同檔案時都列出來，例如 `原 BUILD-018、REVIEW-018`。
3. **跟 PM 不一致的地方**：PM 寫的、實際、為什麼、待誰處理。「PM 寫的」要以 PM 規格的現行版本為準。
4. **已知限制**：限制、原因、待誰處理。還沒驗證過的寫成「未驗證」並寫明補驗條件，不要寫成已證實的限制。

「待誰處理」只用這幾個詞開頭：`PM`、`後端`、`PM／後端`、`SDK`、`引擎`、`設計`、`需另立票`、`不處理`。有追蹤的 issue 就接在後面的括號裡，例如 `PM（asgard-ai-platform/asgard-sdk-pm#12）`。

編號是 `<章代號>-<n>`，三張表共用同一組號碼。**編號只增不減、不重用**：拿掉的條目，它的編號就不再使用；新條目取這一章在 git 歷史裡出現過的最大號再加 1（`git log -p -- requirements/spec/<章>.md | grep -oE '<章代號>-[0-9]+' | sort -t- -k2 -n | tail -1`）。

新 BUILD 引用時：沿用的是既有行為，就指向 PM 規格或程式；只有引用設計決定時才寫 `← spec/<ID>`。

## 反覆修改過的功能

只寫最終狀態，不保留「原本是…後來改成…」。只有在舊做法看起來比較自然、agent 可能改回去時，才在「設計決定」寫一條「不要做 X，因為 Y」，類型標 `刻意的行為`。PM 需求還在變的，記進「已知限制」。

## 什麼時候收斂

一對 BUILD／REVIEW 要同時符合下列條件，才可以開始收斂：

- 它對應的 PM issue 在 GitHub Projects 看板上是 **Done**（`In review`、`Pending fix` 都不算），**而且**
- BUILD 與 REVIEW 本身的 Status 都是 `done`。

沒有 PM 票的，跟著它的來源票一起收；沒有來源票的，要合併並發版（打 tag）後才收。舊格式的 `TASK-*.md`、FOLLOWUP、測試報告等開發過程文件，用同樣的條件判斷；它依附的上游票還沒結案，就不收。

符合條件只代表可以開始收斂，不代表可以刪。能不能刪，看下一節。

## 收斂步驟

1. **固定比對基準**：記下這次比對用的程式 commit 與 PM submodule commit。PM 的 pin 落後 PM `main` 時，先更新 submodule（獨立的 PR），再開始收斂。
2. **逐項盤點要刪的檔**：把每個檔裡的設計決定、理由、否決的方案、刻意偏離、REVIEW 沒解的發現、延後的工作、沒驗證的部分逐項列出來，每項標一個去處：**承接**（寫明在哪一章、哪一條，或哪一處程式註解）、**已失效**（寫明被哪張票或哪段程式推翻）、**純歷史**（開發過程，不影響之後的修改）、**待確認**（還判斷不了）。**還有「待確認」的檔不可以刪。** 刻意偏離、沒解的缺陷、沒驗證的部分，不管嚴重度高低都要有去處。
3. **寫進章節**：以現在的程式和 PM 規格的現行版本為準，不要照 BUILD 當時的描述寫。先修正寫錯的條目，再補新的。
4. **登記封存索引**：在 [`converged-tasks.md`](converged-tasks.md) 為每個要刪的檔各登記一列，附刪除前最後一個 commit 的連結；「收進」只寫章名。被其他檔取代的，要註明取代它的是哪一個。
5. **更新引用**：`requirements/` 裡指向這些檔案的連結改成指向章節；程式碼註解寫了已刪檔案的完整路徑的，改成指向規格章節；只寫編號的不用改，封存索引查得到。
6. **從 Task Queue 移除並刪檔**：從 `requirements/tasks/_index.md` 移除對應的列，刪除原檔。
7. **檢查連結**：`requirements/` 底下沒有新增失效的相對連結。

刪除只代表「內容已經搬到這裡」，不代表那張票的所有需求都已交付；未交付的部分記在「跟 PM 不一致的地方」或「已知限制」。
